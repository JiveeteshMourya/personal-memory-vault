# Phase 03 — User Authentication

> **Status:** ✅ Done · **Depends on:** 01 (shell), 02 (db) · **Unlocks:** 04, 05 and every owner-facing feature

## Goal

The vault owner can sign up, sign in and sign out. The dashboard is only reachable when signed in. The rest of the app identifies the owner through one DAL function.

## Coupling boundary

- **Owns:** the Better Auth config, its tables (`src/db/schema/auth.ts` and its migration), the auth pages and actions (`src/app/(auth)/`), the auth route handler, `src/proxy.ts`, `src/data/auth.ts`, and the shell's user menu.
- **Must not:** let anything outside `src/lib/auth*.ts` and `src/data/auth.ts` import Better Auth directly.

## Decisions (made with the user, 2026-11-15)

- **Auth library:** Better Auth 1.7 _(given)_.
- **Sign-in methods:** email + password only. Google OAuth _(past)_ was not picked.
- **DB adapter:** Better Auth's Drizzle adapter (`provider: "pg"`, `usePlural: true`). The tables live in `src/db/schema/auth.ts` and are applied through `db:generate` + `db:migrate`, like every other table.
- **User id type:** UUIDs (`advanced.database.generateId: "uuid"`), generated by Postgres. This matches Phase 02's "IDs are UUIDs" contract, so feature tables use `uuid("user_id")`.
- **Table names:** plural (`users`, `sessions`, `accounts`, `verifications`). This avoids Postgres's reserved word `user` (`select * from user` silently returns the current role) and matches the plural feature tables.
- **Forms:** Server Actions + `useActionState`, validated with zod on the server. react-hook-form and Better Auth's React client were not picked.

## Skills / plugins

- `better-auth-best-practices` and `create-auth` from `better-auth/skills` (official), installed for this phase only and removed afterwards, since no later phase builds auth. Their Claude plugin bundles the same two skills, so no plugin was installed.
- A later phase that changes Better Auth config (for example the 2FA or email-flow backlog items) re-adds `better-auth-best-practices` for that phase only.
- Bundled Next.js guides read: `01-app/02-guides/authentication.md` and `authentication-with-cache-components.md`.

## In scope (MVP slice)

- `src/lib/auth.ts` (the server instance, plus `authHandler`) and the route handler `src/app/api/auth/[...all]/route.ts`.
  - **No client helper (`auth-client.ts`).** With Server Actions, nothing on the client calls Better Auth.
- Pages `/sign-in` and `/sign-up` in the `(auth)` route group, styled with the Phase 01 primitives. Sign-out lives in the shell's user menu.
- `src/proxy.ts`: an **optimistic** redirect of `/dashboard/*` to `/sign-in` when there is no session cookie.
  - **Signed-in owners are sent away from the auth pages by the `(auth)` layout**, using a real session check. The proxy doesn't do it, because a stale cookie would loop between the two pages (see the handoff notes).
- `src/data/auth.ts`:
  - `getCurrentUser = cache(async () => UserDTO | null)`
  - `requireUser(): Promise<UserDTO>`, which redirects to `/sign-in` when there is no session
- The user's name and email in the shell header.
- Env vars: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`.

## Out of scope → hardening backlog

- Email verification, password reset, 2FA, lockout and throttling (already seeded). Account deletion is in the backlog's Sprint cut. This phase adds more items; see the backlog.

## Contract provided

- **DAL:** `import { getCurrentUser, requireUser } from "@/data/auth"`, with `UserDTO = { id, name, email }`.
  - Both read the request, so a page or layout that calls them renders that part behind `<Suspense>` (Cache Components).
  - Every feature DAL function that reads or writes the owner's data calls `requireUser()` itself; never trust the proxy.
- **Owner id:** `users.id` is the vault owner id, a **uuid**. Every feature table references it as `user_id`:
  ```ts
  import { users } from "./auth";
  userId: uuid("user_id")
    .notNull()
    .references(() => users.id, { onDelete: "cascade" });
  ```
- **Routes:** `/sign-in`, `/sign-up`. `/dashboard/*` is protected.
- **Mutations:** the auth Server Actions (`signUp`, `signIn`, `signOut`) live in `src/app/(auth)/actions.ts`.

## Deliverables

Auth config and migration, auth route handler, auth pages and actions, `src/proxy.ts`, `src/data/auth.ts`, the shell user menu, env vars.

## Acceptance criteria & verification

- [x] Sign up → you land on `/dashboard`. Sign out → `/dashboard` redirects to `/sign-in`.
- [x] A Server Action or DAL call that needs a user fails without a session, even if the proxy is bypassed.
- [x] Two accounts each see only their own name in the shell.
- [x] Lint, typecheck, tests and format pass.

## Outcome & handoff notes

**Built:**

- **Library:** `better-auth` 1.7.25. Telemetry is off by default in 1.7, so there's nothing to configure.
- **Config (`src/lib/auth.ts`):**
  - `secret` and `baseURL` come from the validated `env`.
  - The adapter is `drizzleAdapter(db, { provider: "pg", usePlural: true })`, with `emailAndPassword: { enabled: true }`. Defaults apply: auto sign-in after sign-up, 8–128 character passwords, 7-day sessions.
  - `generateId: "uuid"`: on Postgres, Better Auth leaves the id empty and the column default (`gen_random_uuid()`) fills it.
  - `nextCookies()` is the last plugin, so Server Actions can set and clear the cookie.
  - `authHandler = toNextJsHandler(auth)` is exported for the route file, so the route doesn't import `better-auth`.
- **Schema (`src/db/schema/auth.ts`, `drizzle/0001_auth.sql`):**
  - Better Auth's four core tables.
  - The JS keys are Better Auth's field names (the adapter maps by them); the columns are snake_case.
  - uuid ids, timestamptz everywhere, cascading FKs to `users`, and the indexes `sessions_user_id_idx`, `accounts_user_id_idx`, `verifications_identifier_idx`.
  - Unique `users.email`: Better Auth lowercases emails on both sign-up and sign-in.
- **DAL (`src/data/auth.ts`):**
  - `getCurrentUser` calls `auth.api.getSession`, which checks the session row on every call (no cookie cache, so revocation is immediate). It returns only `{ id, name, email }`.
  - **Auth-page helpers (not part of the contract):**
    - `signUpWithEmail` and `signInWithEmail` map Better Auth's `APIError` codes (`USER_ALREADY_EXISTS*` → `email_taken`, `INVALID_EMAIL_OR_PASSWORD` → `invalid_credentials`) and rethrow anything else.
    - `endSession` signs out the current session.
- **Actions (`src/app/(auth)/actions.ts`):**
  - zod validation with field errors via `z.flattenError`.
  - `values` refills name and email after React resets the form. The password is never returned.
  - `redirect("/dashboard")` on success.
- **Pages:**
  - The `(auth)` layout holds the logo, theme toggle and a centered column, plus `<Suspense><RedirectIfSignedIn /></Suspense>`.
  - The forms are client components using `useActionState`, built from `FieldGroup`/`Field`/`FieldError`.
  - `noValidate`, so every error comes from the server and reads the same way.
  - Correct `autoComplete` values, and `aria-invalid` / `aria-describedby` on invalid fields.
- **Proxy (`src/proxy.ts`):** matcher `/dashboard/:path*`. It redirects (307) to `/sign-in` when `hasSessionCookie` (`src/lib/auth-cookie.ts`, which wraps `getSessionCookie`) finds no cookie.
- **Shell:**
  - `UserMenu` is an async Server Component calling `requireUser()`. Its trigger shows an initials avatar plus the name (name hidden below `sm`); the menu shows name, email and "Sign out".
  - `AppShell` wraps it in `<Suspense fallback={<UserMenuSkeleton />}>`.
  - `SignOutItem` (client) calls the `signOut` action in a transition.
- **Env:** `BETTER_AUTH_SECRET` (min 32 chars) and `BETTER_AUTH_URL` are validated in `env.ts`, documented in `.env.example`, and given placeholders in `test/setup.ts`.
- **Tests (local, git-ignored):** 30 pass, including:
  - **DAL:** the DTO shape, the `requireUser` redirect, error mapping.

  - **Actions:** field errors without calling the DAL, no password echo, trimming, redirects, sign-out.

**Verified:**

- **Migration:** `db:migrate` created `users`, `sessions`, `accounts` and `verifications` (uuid ids, timestamptz). Re-running it is a no-op.
- **Routes:** `GET /api/auth/ok` returns `{"ok":true}`. `/dashboard` and `/dashboard/memories` without a cookie return a 307 to `/sign-in`. `/api/v1/health` is still `ok`.
- **Sign-up via the HTTP endpoint:** a uuid id generated by Postgres and a lowercased email. `/dashboard` with the cookie rendered the name and email. `/sign-in` with the cookie redirected to `/dashboard`.
- **Server Actions, as no-JS form posts:**
  - **Invalid input:** inline errors, and the name is kept.
  - **Valid sign-up:** 303 to `/dashboard` with an `HttpOnly; SameSite=lax` session cookie, and the padded email was trimmed.
  - **Duplicate email:** "An account with this email already exists."
  - **Wrong password:** one `role="alert"` message, the email is kept, and the password appears nowhere in the response.
  - **Right password:** 303 to `/dashboard`.
- **Sign-out** (the `Next-Action` call the client makes): the cookie is cleared, the session row is deleted, the action redirects to `/sign-in`, and `/dashboard` then returns a 307 to `/sign-in`.
- **Proxy bypass:** `/dashboard` with a forged `better-auth.session_token` passes the proxy, but `requireUser()` in the user menu redirects to `/sign-in`.
- **Two accounts:** the second account's dashboard showed only its own name.
- **Logs:** Better Auth logs `WARN [Better Auth]: Invalid password` on a failed sign-in, with no email or other PII.
- **Checks:** the next-devtools MCP `get_compilation_issues` returned none. Lint, typecheck, tests, format and build pass. The build shows the dashboard routes and the auth pages as partially prerendered (◐).
- The probe accounts were deleted afterwards. Browser checks are by the user.

**Gotchas for later phases:**

- **Read the user behind `<Suspense>`.** `getCurrentUser`/`requireUser` read `headers()`. Under Cache Components, a page that awaits them at the top level fails the build. Push the read into a component inside `<Suspense>`, or call it from a DAL function used inside one.
- **Feature DAL pattern:** start with `const user = await requireUser();` and filter every query by `user.id`. In Server Actions and Route Handlers, React `cache` doesn't dedupe; each call checks the session again, which is fine.
- **Redirects inside a stream:** `redirect()` in a Suspense'd component arrives after the static shell has been sent. The browser follows it with a meta refresh plus a client redirect. Anything in the static shell is visible before that, so **never put owner data outside the boundary.**
- **Why the proxy is one-way:** if it also sent cookie-holders away from `/sign-in`, a stale or revoked cookie would loop forever (proxy → `/dashboard` → `requireUser` → `/sign-in` → proxy → …). The `(auth)` layout's real session check handles that direction.
- **`nextCookies()` must stay the last plugin.** Without it, `auth.api.signInEmail` etc. in a Server Action don't set the cookie.
- **Better Auth CLI:** `auth generate` refuses `src/lib/auth.ts` because of its `server-only` import (even with `--conditions=react-server`). After adding a plugin that brings its own fields or tables, edit `src/db/schema/auth.ts` by hand (the field names are in Better Auth's docs or `@better-auth/core`'s `get-tables`), then run `db:generate`.
- **Rate limiting:** Better Auth's built-in rate limiter skips server-side `auth.api` calls, so the Server Action sign-in has no throttling yet (backlog). It only covers direct `/api/auth/*` HTTP calls.
- **`BETTER_AUTH_URL` must match the origin the browser uses.** Better Auth rejects requests from other origins. Set it to the deployed URL if the vault is ever deployed.
- **Restart `bun dev` after changing `BETTER_AUTH_*`**, because the server validates env at startup.
- **The secret signs every cookie.** Changing `BETTER_AUTH_SECRET` signs everyone out.
