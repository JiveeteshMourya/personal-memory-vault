## Session protocol (every phase)

1. Start a **fresh agent session** for the phase.
2. Read these before doing anything else:
   - `AGENTS.md`
   - this index, including the [Decisions Log](#decisions-log)
   - [main-project-objective.md](../main-project-objective.md)
   - the phase doc
   - the **Outcome & handoff notes** of every phase it depends on
3. **Ask the user which libraries/packages to use.** The phase doc lists options, with the user's past picks marked. Install nothing before the answer.
4. **Agent tooling:** check what the chosen libraries actually need against the [Agent tooling](#agent-tooling) rules. Most phases need nothing new. Propose any addition to the user with the reason, and install it only on a yes.
5. Read the relevant guides in `node_modules/next/dist/docs/` before writing Next.js code. This version differs from training data.
6. Plan in plan mode, get approval, then implement.
7. Verify against the phase's acceptance criteria. Use the `next-devtools` MCP for runtime checks (errors, routes, logs, compilation issues) while `bun dev` runs, plus manual checks in the browser.
8. Append anything deliberately skipped to [hardening-backlog.md](hardening-backlog.md).
9. **Prune agent tooling:** remove every skill, plugin and MCP server that no remaining phase needs, and update the [installed list](#agent-tooling).
10. Fill in the phase's **Outcome & handoff notes**, set its status here, update the progress count, and add rows to the [Decisions Log](#decisions-log).
11. Commit only when the user asks.

## Sprint mode (until the 2026-11-17 demo)

Phases 06–09 run in sprint mode. It overrides the session protocol above where they differ:

- **Libraries are pre-decided** in the [Decisions Log](#decisions-log). Skip step 3 unless the phase needs something not listed there, and ask before adding anything new.
- **Tests:** unit tests only for the policy engine (Phase 06). Each API phase extends `scripts/smoke-api.sh` (curl) instead.
- **Verification:**
  - `bun run lint`, `bun run typecheck`, `bun run build` and `bun run format:check`
  - the smoke script
  - the next-devtools compile and error check
  - a quick browser check by the user
- **Docs:** outcome notes are 10 bullets or fewer (contract changes, env vars, gotchas). Backlog items are one line each.
- **Scope:** demo-grade over production-grade. The privacy invariants still hold in full.
- Both projects run only on this PC: the vault on `:3000`, the hub on `:3001`, and Postgres and Pinecone Local in Docker. Nothing is deployed.

## Agile principles

- Build the **simplest end-to-end slice** that meets the phase goal: the happy path, input validation, and the auth/permission checks the feature needs.
- No speculative abstractions, config knobs or "future-proofing". A little duplication beats a premature helper.
- **Never leave a known bug in.** Rare edge cases, scale and performance work, and defense-in-depth go to the [hardening backlog](hardening-backlog.md) instead of being built now.
- Privacy invariants are **not** optional, even in an MVP:
  - default deny
  - authorize _before_ retrieval
  - encrypt memory content
  - never send unauthorized data to an app or an LLM
  - never log memory content
- **Edits must feel native.** A change to an existing feature reshapes it as if it had always been designed that way (see `AGENTS.md`).

## Loose-coupling rules

- A phase depends only on the **Contract provided** section of other phases, never on their internals.
- Each feature phase owns its tables (its own migration), its Data Access Layer module(s), its UI route(s) and its tests.
- If a phase is redone with a different approach, either keep its contract or record the migration in the [Pivot Log](#pivot-log) and update the affected phase docs.
- Phases can be reordered as long as their dependencies are met.

## Conventions (standard Next.js practice)

The source of truth is the bundled docs in `node_modules/next/dist/docs/`, especially `01-app/02-guides/data-security.md` and `01-app/02-guides/authentication.md`.

| Concern              | Where                                                                                                  | Rule                                                                                                                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Data Access Layer    | `src/data/<domain>.ts`                                                                                 | `import "server-only"`. The only code that touches the database or vector index. Performs authentication and authorization checks. Returns minimal **DTOs**, never raw rows. This is where the vault's privacy guarantees live.                   |
| Reads in UI          | Server Components (`page.tsx`, `layout.tsx`)                                                           | Call DAL functions directly.                                                                                                                                                                                                                      |
| Mutations from UI    | Server Actions in `actions.ts` next to the route                                                       | `"use server"`. Validate input, call the DAL, `revalidatePath` / `updateTag`, and return only what the UI needs.                                                                                                                                  |
| External app API     | Route Handlers in `src/app/api/v1/**/route.ts`                                                         | Only for connected apps calling over HTTP. Validate input, call the DAL, return `Response.json(data, { status })`. Errors use `{ error: { code, message, details? } }` with standard status codes (400/401/403/404/409/500).                      |
| Route protection     | `src/proxy.ts`                                                                                         | Optimistic redirects only. The real checks live in the DAL.                                                                                                                                                                                       |
| Clients & infra      | `src/lib/`                                                                                             | Validated env (`env.ts`), db, auth, crypto, `pinecone.ts`, `ai.ts`, and so on, as lazy singletons.                                                                                                                                                |
| UI components        | `src/components/ui/` (primitives), `src/components/` (shared), `src/app/**/_components/` (route-local) | Server Components by default; add `"use client"` only where interaction needs it.                                                                                                                                                                 |
| Shared domain types  | Co-located by default; `src/types/` only for types used across features                                | —                                                                                                                                                                                                                                                 |
| Naming               | Files and route segments in kebab-case; React components as PascalCase named exports                   | —                                                                                                                                                                                                                                                 |
| Tests                | Co-located `*.test.ts`, run with `bun run test` (`bun test --isolate`)                                 | Git-ignored (`*.test.*`, `*.spec.*`): tests stay local and are never committed. `bun fmt` skips them too. Isolation gives each file a fresh module registry, so one file's `mock.module()` can't leak into another (plain `bun test` shares one). |
| Formatting           | `bun run format`                                                                                       | Settings come from `bunfig.toml` (double quotes, semicolons, 2 spaces, width 100).                                                                                                                                                                |
| Public API reference | `docs/public-api.md`                                                                                   | The `/api/v1` contract. ## Agent tooling

Every skill description, plugin and MCP tool list is loaded into **every** session, so each one costs context whether it's used or not. Keep the set to what the remaining phases need.

**Installed now:**

| Tool                               | Kind              | Why it stays                                 | Remove after                 |
| ---------------------------------- | ----------------- | -------------------------------------------- | ---------------------------- |
| `shadcn`                           | skill             | UI phases add and compose shadcn components  | Phase 09 (the last vault UI) |
| `supabase-postgres-best-practices` | skill             | Feature phases add tables, indexes, queries  | Phase 09 (the last schema)   |
| `next-devtools`                    | MCP (`.mcp.json`) | Runtime checks in every phase's verification | —                            |

**Rules:**

- **Need, not nice-to-have.** Install only what this phase's work calls for, when nothing installed or bundled already covers it. Skip general "best practices", review, design and workflow skills: `AGENTS.md`, this index, the bundled Next.js docs and the existing code are the guidance.
- **Smallest unit.** Prefer a single skill over a plugin, since a plugin can also bring MCP servers, commands and agents. Take only the skill you need from a repo, not all of it. Don't add an MCP server for a service that isn't set up yet.
- **Official only, ask first, project scope only.**
  - Skills: `bunx skills add <owner/repo> --skill <name> -a claude-code -y --copy` (writes `.claude/skills/` and `skills-lock.json`).
  - MCP servers: `.mcp.json`. Plugins: `.claude/settings.json`.
  - Never install globally. If a skill asks for a global install, ask the user first.
  - Read every installed `SKILL.md` before relying on it.
- **Prune at phase end.** Delete the skill folder and its `skills-lock.json` entry, the `.mcp.json` server, or the `enabledPlugins` entry. Record why in the Decisions Log so no later session adds it back.
- **Account-level extras stay off.** claude.ai sends its own connectors, plugins and skills (`docx`, `pdf`, `pptx` and others) into every session. This project turns them off, without touching user-level settings:
  - `.claude/settings.json` (committed): `"disableClaudeAiConnectors": true`
  - `.claude/settings.local.json` (git-ignored, per machine): `"syncClaudeAiPlugins": false` and `"syncClaudeAiSkills": false`. Claude Code reads these two only from local or user settings, so recreate the file on a new machine.
- **Claude Code's built-in skills stay on** (`claude-api`, `dataviz`, `run` and others). They ship with the tool and aren't installs. Use them where a phase doc names them.
